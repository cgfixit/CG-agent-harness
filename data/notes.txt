Three different "memory" problems. Do not treat them as one knob.

1. Harness memory is disk under ~/.CGagentHarness. Pinned notes and
   structured memory cannot authorize tools, coding, or network. Mode 0600
   is not encryption. Compaction (chat.compact_prompt_tokens seeded 24000,
   keep 8) shrinks the next on-disk prompt. It does not free KV and it
   does not reserve RAM. Immediate GPU release is not claimed.

2. KV cache is the attention K/V working set inside Ollama or MLX. It
   grows with layers, KV heads, head dim, sequence, and batch. The harness
   never sends num_ctx (ollama.rs, INVARIANTS.md, MODELS.md). The server
   window is whatever Ollama was started with. Seeded web.total_tokens
   28000 and evidence_tokens 6000 assume a verified 32768 window. If you
   cannot verify it, home config stays 16000/3000. Existing homes are not
   rewritten. Confirm with a short generate that does not send num_ctx,
   then curl 127.0.0.1:11434/api/ps. context_length must match the budget.
   OLLAMA_CONTEXT_LENGTH=32768 before ollama serve (or launchctl setenv,
   then full quit). OLLAMA_CONTEXT is not the documented lever.
   finetune/Modelfile.cgagent PARAMETER num_ctx 32768 is the GGUF re-export
   only, not the live chat path.

3. Host memory pressure is the OS or hypervisor reclaiming that working
   set. On the 48GB M5 Pro there is no VMware balloon. The analog is
   macOS compressor / jetsam: weights + KV + OS + other apps over the
   unified pool, decode stalls, then ReadTimeout or "model server
   unreachable". In a VMware guest the mechanism is balloon (vmmemctl),
   compression, and .vswp. Same symptom, different knob. A ballooned
   guest can report the stall while /api/ps still says 32768. Quantizing
   KV does not fix an overcommitted VM; a reservation does not fix a
   4096 server window.

parse_chat_response accepts only finish_reason "stop". "length" is a
typed truncation error ("reduce the requested output or adjust the
configured token budget"). Any other reason, including null, is "did not
report a normal completion (finish_reason=stop required)". No retry.
That is why a Codex-style short tool loop feels smoother: one truncation
there is one cheap step; here it fails the whole chat, web, or /loop
turn. Web tool turns also require finish_reason "tool_calls" before the
dispatcher runs. Cloud chat is a different client (Claude end_turn, Grok
completed) and is not this path.

Use which model for which job (48GB unified, not a VMware guest):

- qwen3.8:27b at a verified 32768. Default for planner and hard coding.
  Quality over context. fp16 KV at 32k is on the order of several GB
  (q8_0 roughly halves that). 128k on this class is tens of GB of KV
  plus ~18GB weights and does not fit beside the OS. The harness seed
  is 32k because that is the verified window, not because 32k is a
  hardware constant. OLLAMA_KV_CACHE_TYPE=q8_0 and OLLAMA_FLASH_ATTENTION=1
  are Ollama process env, not harness keys. They are a quality trade.
  Keep OLLAMA_NUM_PARALLEL=1. Do not drop to 7B just to chase context
  if the failure is a 4096 server window.

- 7B-8B class (qwen2.5:7b, qwen3:8b, qwen2.5-coder:7b) when the job is
  long evidence: web synthesis, big logs, stuffed goal context. Advertised
  window is 128k. Weights ~5GB. fp16 KV at 128k is on the order of
  ~5-8GB for a 7B GQA model, not "zero pressure", and not 40GB free.
  Weights + KV + overhead land nearer 12-20GB. 128k fits. Past the
  trained window, RAM fit is not quality. Sweet spot is the trained
  window, usually 128k, after /api/ps proves it.

- 14B coder when 7B quality is not enough and 27B at 32k keeps
  truncating. 128k fits with less headroom than 7B. Still verify
  context_length. Still not a harness num_ctx.

- 20B-class MoE only if the exact tag is installed and /api/ps proves
  the window. Tighter than 8B. Not a default.

Do not wire num_ctx 131072 into the harness model list. /model use
changes the chat tag only; the planner has its own tag and base_url.
A Modelfile PARAMETER num_ctx or OLLAMA_CONTEXT_LENGTH is the server

Config levers that are real, and what they are for:

- Server window first. Almost every "model did not report a normal
  completion" on a fat web or goal turn is finish_reason=length or a
  non-stop reason because the live window is below the budget. Fix the
  window or lower the budget. Do not start with a smaller model.

- warmup.keep_alive_sec seeded 300, allowed 1-3600, sent as keep_alive,
  never num_ctx. Raise toward 1800-3600 only if web research (plan,
  plan, synthesis) unloads the model between calls. Does not enlarge KV.
  Existing homes keep their value.

- reasoning_effort "none" is already the seed. Leave it. Thinking-mode
  token use is a model behavior, not a second harness budget I verified
  in this pass.

- web.model_tokens seeded 1024 (256-2048) is the synthesis completion
  cap. Trim this and evidence_tokens when web turns return length.
  Trim total_tokens when the prompt itself overflows.

- agentic.deepagent_github.retrieval.enabled ships off (literal true
  only). Child-only Tantivy over the clone jail. Cuts pasted planner
  context. Does not run on cloud proposers, does not arm writes, does
  not change chat or /loop.

- /loop is a separate tighter budget (harness_loop_rate_limit,
  max_requests seeded 8). Keep goals atomic. Do not quote a 2048
  max_tokens or a 5-minute window until you read the home file. /loop
  is not /agent.

Not config. Do not do these from advice:

- Retry on finish_reason=length. Real gap vs Codex. Behavior change in
  the parse_chat_response callers. One concern, draft PR, grok/ branch.
- Whitelist null or "eos" for MLX. Also a code change. MLX is loopback
  OpenAI-compatible only; an -mlx tag does not prove the backend.
- Per-call num_ctx. The invariant is that pull and chat never send it.
  Logging /api/ps context_length at warmup is the compatible version
  of that idea.

VMware only if Ollama actually runs in a guest. Reservation at or above
weights + peak KV + OS, balloon off or pinned, no overcommit. Then the
same /api/ps check. Harness compaction still only shrinks the next
prompt. On the Mac, skip the balloon work and treat compressor stalls
as the same working-set rule.

Bottom line: **smaller model wins.** Context on 48 GB is just "whatever's left after the weights fit." Your 27B is too big to hold a large KV cache, which is exactly why it's capped at 32k. To get *more* context, drop to the **7B–8B class** — those support 128k and leave ~40 GB for the cache, so 128k runs comfortably and you can even push toward 192–256k.

**The immediate answer — you already have it:**

The `qwen2.5:7b` (4.7 GB) on this machine supports **128k context**. On 48 GB you could even raise it past that. No download needed:

```
OLLAMA_CONTEXT=131072 ollama run qwen2.5:7b
# or bake it in:
PARAMETER num_ctx 131072
```

That alone takes you from 32k → 128k, zero RAM pressure (weights + cache ≈ 18 GB of your 48 GB).

**The math (why small = more context):**

KV cache grows linearly with context length. Budget for cache on this box ≈ 48 GB − weights − ~4 GB overhead.

| Model class | Weights | Max context | Fits 48 GB at full context? |
|---|---|---|---|
| **7–8B** (Qwen2.5-7B, Qwen3-8B, Llama3.1-8B) | ~5 GB | **128k** | ✅ easily, ~18 GB total — *most context* |
| 14B (Qwen2.5-Coder-14B, Qwen3-14B) | ~9 GB | 128k | ✅ ~33 GB total |
| 20B (GPT-OSS-20B, MoE) | ~13 GB | 128k | ✅ but tight |
| **32B / 27B (what you run)** | ~18 GB | 128k advertised | ❌ ~50 GB needed → **capped at 32k** |
clearly I need to revisit memory pressure outside of a vmware context although prob similar

**Recommendation for this harness (coding agent):**

- **Best all-round:** `qwen3:8b` — strong general + coding, 128k, ~5 GB.
- **Coding-optimized:** `qwen2.5-coder:7b` or `qwen2.5-coder:14b` — 128k, tuned for code. 14B still fits.
- **Strongest agent in the class:** `gpt-oss:20b` — 128k, ~13 GB, fits but less headroom.

One caveat on "more context": 128k is where these models are actually *trained/extended* to. Pushing a 7B to 256k fits in RAM but quality degrades past the trained window — 128k is the real sweet spot on 48 GB.
