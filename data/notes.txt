Here's the honest picture: most of the "errors" you're hitting are not the model being dumb — they're the harness's strict contract colliding with the server's actual context window, plus a few Codex-style behaviors your harness deliberately doesn't have. Breaking it down:

## Why Codex + qwen feels smoother

Codex runs qwen as a **tool-calling loop with small incremental prompts**: each turn is short, the model emits one structured tool call, gets a small result back, and repeats. Failures are cheap and retried per-step. Your harness instead does **big single-shot completions** (chat turn, web synthesis, /loop plan) with a hard rule: `finish_reason` must be exactly `"stop"`, or the whole turn errors out (openai_chat.rs `parse_chat_response`). One truncation = one user-visible error, no retry. That's the core smoothness gap.

## The #1 suspect: your server window isn't what the config assumes

The harness **never sends `num_ctx`** — it inherits whatever Ollama was started with, and the config is sized for a **verified 32768** window. If Ollama is actually running at its default (4096), every fat web-research or goal prompt blows the window, the model returns `finish_reason=length`, and you get "model response did not report a normal completion" / truncated-output errors. Check:

```
OLLAMA_CONTEXT_LENGTH=32768 ollama serve
curl 127.0.0.1:11434/api/ps   # context_length must read 32768
```

If `/api/ps` shows anything smaller (or you can't verify), config.default.yaml itself tells you the fallback: `web.total_tokens: 16000`, `web.evidence_tokens: 3000`, `chat.compact_prompt_tokens` correspondingly lower. Running 28k web budgets against a smaller real window is guaranteed errors.

## Concrete config levers (no code changes)

1. **KV cache + parallelism on 48GB**: start Ollama with `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0` — a 32k KV cache for a 27B model is several GB in fp16; q8_0 halves it and prevents memory pressure that causes mid-request stalls (which surface as `ReadTimeout` errors). Keep `OLLAMA_NUM_PARALLEL=1`.
2. **`warmup.keep_alive_sec: 300 → 1800–3600`**: web research does multiple model calls over minutes (2 planning rounds + synthesis). At 300s the model unloads between phases and you pay a reload (and a possible stall) mid-flow. Longer keep-alive = fewer "model server unreachable" flakes.
3. **`reasoning_effort: "none"`** — you already have this; keep it. With qwen3 thinking enabled, the 2x reservation halves your effective max_tokens and truncations get much more likely.
4. **`web.model_tokens`** (synthesis completion, default 1024): fine. But if you see `finish_reason=length` specifically on web turns, this plus `evidence_tokens` is where to trim first.
5. **`agentic.deepagent_github.retrieval.enabled: true`**: ships off. Turning it on lets the planner pull 3 small file excerpts instead of you pasting big context — smaller prompts, fewer window overflows on goal/loop work.
6. **`/loop` has its own tight budget**: `harness_loop_rate_limit.max_tokens: 2048` and 8 requests / 5 min. Keep loop goals small and atomic; a sprawling goal guarantees truncation errors at 2048.

## Code-level gaps vs Codex (PR candidates)

These are the real "make it feel like Codex" changes, each small and reviewable:

1. **Bounded retry on `finish_reason=length`**: on truncation, retry once with a smaller `max_tokens` (or trimmed context) instead of erroring the turn. Single biggest smoothness win — converts the most common error into a silent recovery. Lives in `parse_chat_response` callers.
2. **Fallback-reason tolerance for MLX servers**: some OpenAI-compatible local servers report `finish_reason` inconsistently (`null`, `"eos"`). Whitelist additional terminal reasons when usage shows a completed short output, so MLX/LM Studio backends don't error on cosmetic differences.
3. **Loop step-wise decomposition**: instead of one 2048-token plan response, iterate plan→step→step with per-step calls (Codex shape). Bigger change, would slot behind the existing loop budget.
4. **Per-call `num_ctx` probe logging**: log the `/api/ps` context_length at warmup and warn in audit if it diverges from what `web.total_tokens` assumes — turns silent misconfiguration into a loud, actionable line.

**The immediate answer — you already have it:**

The `qwen2.5:7b` (4.7 GB) on this machine supports **128k context**. On 48 GB you could even raise it past that. No download needed:

```
OLLAMA_CONTEXT=131072 ollama run qwen2.5:7b
# or bake it in:
PARAMETER num_ctx 131072
```

That alone takes you from 32k → 128k, zero RAM pressure (weights + cache ≈ 18 GB of your 48 GB).

**The math (why small = more context):**

KV cache grows linearly with context length. Budget for cache on this box ≈ 48 GB − weights − ~4 GB overhead.
